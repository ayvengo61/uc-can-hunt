==========================================================
 ЗАПУСК ДВОЙНЫМ КЛИКОМ: UC_H503_Monitor.exe
==========================================================

Запусти UC_H503_Monitor.exe. Python, pyserial и start.bat больше
не нужны. Программа сама:
 - находит COM-порт контроллера (USB, VID 0483; VCP от ST-Link
   и Bluetooth-порты пропускает);
 - читает JSON-кадры диагностики;
 - открывает приложение настроек отдельным окном (Edge/Chrome
   без адресной строки): http://127.0.0.1:8503/app
   Старый дашборд H503 — http://127.0.0.1:8503/ (кнопка
   "Старый дашборд" в разделе "Инструменты" приложения).

В окне программы видно: есть ли связь, номер порта, счётчик
кадров и журнал (порт открыт / контроллер уснул / порт занят).
Если автопоиск выбрал не тот порт, выбери COM вручную в списке
"Порт". Кнопки: "Приложение", "CAN сниффер", "Совместная работа".
Закрытие окна завершает монитор.

Когда контроллер засыпает и пропадает с USB, монитор ждёт и сам
подключается после пробуждения, даже если номер COM изменился.
Повторный запуск exe второй экземпляр не создаёт, а просто
открывает приложение уже работающего.

Страницы (app.html, dashboard.html, sniffer.html, assist.html)
вшиты в exe. Если рядом с exe лежит файл с тем же именем,
берётся он: правишь файл, обновляешь страницу в браузере.
Exe можно скопировать куда угодно одним файлом.

Монитор общий с G4 и H723: uc_monitor.cs, app.html, sniffer.html
и assist.html одинаковые во всех трёх папках монитора, плата
выбирается при сборке (/define:H503). dashboard.html у H503 свой.

Пересборка (после правки uc_monitor.cs): build_exe.bat.
Нужен только Windows, компилятор csc.exe входит в систему.

Ключи командной строки (необязательные):
  --com COM7     конкретный порт вместо автопоиска
  --port 8600    другой HTTP-порт (по умолчанию 8503, если занят,
                 берётся следующий свободный из десяти)
  --no-browser   не открывать браузер при запуске
  --demo         демо без контроллера: CAN-кадры и эмулятор
                 конфига (порт 18503, отдельно от настоящего)

==========================================================
 ПРИЛОЖЕНИЕ НАСТРОЕК И КОНФИГ
==========================================================

Приложение (/app) читает конфиг командой get, правит set,
сохраняет apply (в журнал во Flash). У H503 ответ get
постраничный: страница не больше 3 КБ, в ней "from" и "next";
приложение просит страницы, пока next не станет 0, и забирает
их через /cfg?since (со старым монитором — по последнему кадру).
В списке "Прошить" файлы, которые монитор записывать не будет
(заходят в журнал конфига или не разобраны), помечены ⛔.

Для своих программ (HTTP монитора, только 127.0.0.1):
  POST /cmd            строка команды в контроллер
                       ({"cmd":"get","sect":"can.0.rx.","from":57})
  GET  /cfg            последний кадр cfg и ответ resp + номера
                       cfg_seq/resp_seq (как у G4/H723)
  GET  /cfg?since=N    то же + "cfgs": ВСЕ кадры cfg с номером > N
                       (последние 64) — страницы не теряются, даже
                       если две пришли между опросами
  GET  /cfg?rsince=N   то же для ответов: "resps"
  GET  /data           телеметрия; кадр {"sig":{...}} (значения
                       сигналов таблиц), который H503 шлёт отдельно,
                       вклеивается в неё полем "sig"
  GET  /board          {"name":"H503","channels":1,
                        "br":[1000,500,250,125],
                        "dbr":[1000,2000,2500,5000],
                        "cfgBase":134332416}  (0x0801C000)
{"cmd":"ping"} — без ответа, держит плату от сна 15 с.

Демо (--demo): встроенный эмулятор конфига H503 (набор "ДЕМО",
узел LIN "губа"): get постранично, set с проверкой типа и
диапазона, apply с проверками и "warn", discard, defaults.
Свой конфиг для демо — файл demo_cfg_H503.json рядом с exe:
{"ключ":значение,...}, "_ro":[...] — только чтение,
"_info":{...} — поля первой страницы (set, code_mask, ...).

==========================================================
 ПРОШИВКА КОНТРОЛЛЕРА (кнопка "Прошить")
==========================================================

Раздел "Инструменты" приложения. Нужен STM32CubeProgrammer
(или STM32CubeIDE — берётся его STM32_Programmer_CLI).

В списке файлов:
 - .elf/.hex из UC_H503*\Debug и Release рядом с папкой монитора;
 - .elf/.hex рядом с exe;
 - готовые прошивки наборов: КОНФИГИ\<набор>\*.elf
   (в списке: "<набор> / файл.elf").

Как идёт прошивка:
 1. монитор шлёт {"cmd":"dfu"} — плата сама перезагружается
    в системный загрузчик (USB DFU), BOOT0 не нужен. Option
    bytes не трогаются: снять питание в любой момент — и плата
    стартует со своей прошивки;
 2. ждёт DFU до 15 с. Не появился (старая прошивка без команды
    dfu) — подсказка: BOOT0 + RESET (или подключить USB с
    зажатой BOOT0), дальше ждёт до 5 минут;
 3. STM32_Programmer_CLI -w файл -v -s: стираются только секторы
    образа, журнал конфига (0x0801C000..0x0801FFFF) остаётся;
 4. готово, когда телеметрия вернулась с маленьким uptime.

Защита журнала: файл, который заходит за 0x0801C000 (конец
образа по сегментам ELF или записям HEX), монитор прошивать
отказывается — запись стёрла бы сохранённые настройки. Такой
файл собран со старым линкером (FLASH 128K), нужен FLASH 112K.

Защищённый чип (ps не "open") прошить нельзя. Снять защиту
можно только ST-Link: ЗАЩИТА\5_снять_защиту_со_стиранием.bat
(стирает весь флеш, включая конфиг).

==========================================================
 CAN / CAN FD СНИФФЕР
==========================================================

Кнопка "CAN сниффер" в окне монитора или ссылка в шапке
дашборда открывает страницу /sniffer. Только приём: сниффер
слушает шину в режиме Bus Monitoring ("молча") и в неё ничего
не передаёт (в диагностике у такого канала "silent":1; car.py
status пишет "молча").

У H503 одна шина CAN (FDCAN1).

Что нужно: прошивка контроллера с модулем app/can_sniff.c
(с 19.09.2026). Со старой прошивкой страница пишет
"прошивка без сниффера".

Включение по каналу:
 - канал всегда слушает шину в режиме Bus Monitoring: без
   подтверждения кадров (ACK), без кадров ошибок и без
   передачи — шину не трогает. Кадры TX конфига на этом канале,
   пока сниффер включён, тоже не уходят;
 - "как в конфиге" — скорость и FD из конфига;
 - своя скорость / FD / скорость данных — канал временно
   перенастраивается на них;
 - режим канала из конфига (Normal, с ACK) — только командой
   {"cmd":"sniff","ch":N,"on":1,"ack":1} (для стенда, где кроме
   контроллера некому подтверждать кадры).
   Скорости данных FD на H503: 1000, 2000, 2500, 5000 кбит/с
   (ядро FDCAN 50 МГц, 4000 и 8000 точно не получаются).

Выключение возвращает канал к параметрам конфига. Пока
сниффер включён, контроллер не засыпает; если монитор закрыли
или кабель вынули, сниффер через 5 с выключается сам.

Страница:
 - "По ID" — таблица: канал, ID, длина, данные, период,
   число кадров. Изменившиеся байты подсвечиваются (ярко —
   меньше 0.3 с назад, тускло — до 3 с). Флаги: 29 — 29-битный
   ID, FD/BRS, ESI, RTR. Клик по заголовку — сортировка.
 - "Лента" — кадры по порядку с временем и интервалом.
 - Фильтр: части ID через пробел (3E8 18DA*), ch0/ch1/ch2 —
   канал, !3E8 — исключить.
 - "Запись в файл" — лог в папку can_logs рядом с exe,
   формат candump (.log): открывается в SavvyCAN и can-utils.
 - Счётчик "потеряно" — кадры, которые не успели уйти в USB
   или переполнили аппаратный буфер контроллера.

Проверка без контроллера: UC_H503_Monitor.exe --demo
(кадры генерирует сам монитор).

Протокол (для своих программ): команда в порт
  {"cmd":"sniff","ch":0,"on":1,"br":500,"fd":1,"dbr":2000}
кадры из порта строками
  ~<канал><флаги> <ID hex> <данные hex | - | R<dlc>> <время мкс hex>


Старый способ (bridge.py + start.bat) оставлен как запасной,
описание ниже.


==========================================================
 UniversalController H503 — Web Monitor (только просмотр)
==========================================================

Веб-морда показывает в реальном времени: входы, выходы PWM,
CAN, LIN, режим STOP, причину последнего сброса и последний
HardFault. БЕЗ редактора конфига (монитор-only).

ТРАНСПОРТ
---------
Родной USB контроллера (PA11/PA12, USB CDC ACM через USBX).
Переходник USB-UART НЕ нужен. В системе устройство видно как
"STM32 Virtual ComPort" / "USB Serial Device", VID 0483 PID 5710.
Скорость (baud) для USB CDC значения не имеет — параметр
оставлен только для совместимости командной строки.

Прошивка шлёт JSON только когда порт открыт (DTR поднят) —
pyserial, PuTTY, TeraTerm делают это сами. Кадр каждые
DIAG_PERIOD_MS (config/diag_config.h, по умолчанию 200 мс).

STOP-РЕЖИМ
----------
Когда контроллер засыпает (CAN молчит STOP_CAN_TIMEOUT_MS),
он отправляет последний кадр с mode="sleeping" и отключается
от USB — COM-порт из системы пропадает. После пробуждения по
CAN устройство enumerate заново, мост сам находит порт
(в режиме auto — даже если номер COM изменился) и продолжает.

БЫСТРЫЙ СТАРТ (Windows)
-----------------------
1. pip install pyserial   (один раз, start.bat сделает сам)
2. Подключить контроллер к USB
3. start.bat
4. http://localhost:8000

ПАРАМЕТРЫ
---------
  python bridge.py [COM] [HTTP_PORT] [BAUD]
  python bridge.py auto 8000            # по умолчанию, автопоиск
  python bridge.py COM7 8000            # конкретный порт

АВТОПОИСК ПОРТА
---------------
Сначала ищется ST (VID 0483), затем на всякий случай
USB-UART мосты (CP210x, CH340, FTDI). Если не нашёл — список
портов выведется в консоль, запусти вручную: python bridge.py COM7

"connected" но frames=0
-----------------------
Контроллер не шлёт JSON. Проверь:
 - config/diag_config.h: DIAG_ENABLED 1
 - порт открыт именно мостом, а не другим терминалом
 - в прошивке VCP_REQUIRE_DTR=1 (app/vcp.c): мост поднимает DTR,
   с экзотическим терминалом без DTR кадров не будет

ПЛАШКИ НА ДАШБОРДЕ
------------------
  rst: por|pin|iwdg|soft   — причина последнего сброса.
       iwdg = зависание/HardFault, подсвечивается красным.
       Рядом, если был HardFault: pc / lr / cfsr — искать pc
       в Debug/UC_H503.map.
  err: последний неудачный HAL-вызов (APP_CHECK): код, строка,
       статус HAL, счётчик. "нет" = всё в порядке.
  CAN: rx — кадры с нашими ID, bus — чужие кадры (активность
       шины), lost — потери FIFO/кольца (должно быть 0).

ФАЙЛЫ
-----
  bridge.py       — мост (читает COM, отдаёт HTTP)
  dashboard.html  — веб-страница (монитор H503)
  start.bat       — запуск
