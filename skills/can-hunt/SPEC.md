# CAN_HUNT — совместный поиск сигналов в CAN машины (Claude + пользователь)

Контракт между частями системы. Все части обязаны следовать ему буквально: формат спецификации
поля, адреса HTTP, схема событий, формат файлов сессии.

## 0. Картина целиком

```
машина ── CAN ── контроллер (G4 / H723 / H503, прошивка со сниффером app/can_sniff.c)
                     │ USB CDC: строки "~..." (кадры) и JSON диагностики
                     ▼
          UC_<плата>_Monitor.exe  (C#, uc_monitor.cs)  ── HTTP 127.0.0.1:<порт>
             │  пишет сессию в папку: frames.log + events.jsonl + meta.json
             │  страница /assist — для пользователя в машине (инструкции, кнопки, живые значения)
             ▼
   Claude в Claude Code (этот ПК): CAN_HUNT/car.py (команды монитору) + CAN_HUNT/canhunt.py (анализ файлов сессии)
```

Цикл работы: Claude даёт инструкцию (`car.py say` / `car.py ask`) → она появляется на странице /assist
крупно, со звуком → пользователь выполняет и жмёт кнопку (кнопка может переключать «фазу» эксперимента) →
Claude получает событие (`car.py wait`, длинный опрос) → анализирует записанную сессию (`canhunt.py`) →
ставит найденное поле в «наблюдение» (`car.py watch`) → пользователь сверяет живое значение с тахометром.

## 2. Спецификация поля (одна строка, везде одинаково)

```
CH:ID:BYTE.BIT:LEN:ORDER[:s][*FACTOR][+OFFSET|-OFFSET]
```

- `CH` — канал 0..2; `ID` — hex (3 цифры std, 8 для 29-битного). **29-битный — ID, записанный 8 цифрами (с ведущими
  нулями: `00000123`), или любой ID > 0x7FF**; иначе 11-битный. 11-битный и 29-битный кадр с одним и тем же числом —
  разные сообщения (canhunt хранит их отдельно). Прошивка UniversalController тип ID определяет по значению
  (> 7FF — 29 бит), поэтому 29-битный ID ≤ 7FF в её конфиг не записать — инструменты об этом предупреждают;
- `BYTE.BIT` — позиция стартового бита, bit 0..7 (0 — младший бит байта);
- `LEN` — длина 1..32 бит; `ORDER` — `le` (Intel) или `be` (Motorola); `:s` — со знаком (дополнительный код);
- физическое значение = raw × FACTOR + OFFSET (по умолчанию 1 и 0). Примеры: `0:0C9:1.7:16:be*0.25`, `1:18DAF110:3.0:8:le`,
  `0:2A0:1.4:1:le`, `0:1F5:0.0:16:le*0.01-40`.

Правила разбора записи — одинаковые в мониторе (C#), canhunt и car.py (`CAN_HUNT\canhunt_lib\specparse.py`), общий
список проверок — `CAN_HUNT\tests\spec_cases.txt` (прогоняется всеми тремя, монитором — `--decodetest OUT spec_cases.txt`):
пробелы только по краям; `CH` — десятичное 0..2; `ID` — 1..8 hex-цифр в любом регистре, `0x` в начале допускается,
не больше 1FFFFFFF; `BYTE` 0..63, `BIT` 0..7, `LEN` 1..32 (десятичные, без знака); `ORDER` обязателен, `le`/`be` в любом
регистре, `:s` тоже; `FACTOR` и `OFFSET` — конечные числа (`0.25`, `.5`, `5.`, `1e-2`, `-40`); поле целиком помещается
в 64 байта данных.

Семантика — как в DBC:
- `le`: старт = МЛАДШИЙ бит значения, позиция p = BYTE*8+BIT; бит i значения берётся из позиции p+i
  (позиция q → байт q//8, бит q%8). Это то же, что `bits_extract()` в прошивке (start_byte, start_bit, bit_len).
- `be`: старт = СТАРШИЙ бит значения, позиция p = BYTE*8+BIT; значение набирается от старшего к младшему:
  взять бит p, затем если p%8==0 → p += 15 (бит 7 следующего байта), иначе p -= 1.
- Если поле выходит за длину данных кадра — значение не определено (не выводить / NaN).

Эталон (обязательный тест во всех реализациях: C#, JS, Python):

| данные | поле | значение |
|---|---|---|
| 1122334455667788 | 0.0:16:le | 8721 |
| 1122334455667788 | 0.7:16:be | 4386 |
| 1122334455667788 | 1.4:4:le | 2 |
| 1122334455667788 | 1.3:12:be | 563 |
| 1122334455667788 | 3.4:12:le | 1364 |
| 1122334455667788 | 7.7:1:le | 1 |
| 1122334455667788 | 2.7:24:be | 3359829 |
| 1122334455667788 | 4.0:32:le | 2289526357 |
| F0FF0080A5C3E17E | 0.0:8:le:s | -16 |

Прошивка UniversalController умеет декодировать только `le` (Intel). Поле `be` длиннее 8 бит, не выровненное так,
что укладывается в один байт, прошивкой пока не читается — инструменты должны это явно помечать.

## 3. Строки кадров от контроллера (уже реализовано в прошивке и мониторе)

`~<канал><флаги> <ID hex> <данные hex | - | R<dlc>> <время, мкс hex>`; флаги: x — 29-бит, f — FD, b — BRS, e — ESI, r — remote.

Команда сниффера (`POST /cmd`): `{"cmd":"sniff","ch":N|-1,"on":1|0,"br":K,"fd":0|1,"dbr":K,"ack":0|1}`. Сниффер
**всегда** поднимает канал в режиме Bus Monitoring («молча»: без ACK, кадров ошибок и передачи; кадры TX конфига на этом
канале, пока сниффер включён, не уходят). Режим канала из конфига (Normal) — только по явному `"ack":1`, без своей
скорости и для канала, включённого в конфиге (для стенда, где кроме контроллера некому подтверждать кадры). Диагностика:
`can[i].silent` — 1, если канал «молча». Без хоста 5 с и после сброса сниффер выключен.

## 4. Время

Единые часы монитора: `Now()` = эпоха UTC в момент старта exe + Stopwatch (секунды, double, мкс-точность).
- События — `Now()` в момент получения/создания.
- Кадры — метка контроллера (мкс), приведённая к `Now()`: при первом кадре после (пере)подключения якорь
  `offset = Now() − ts`; далее медленная подстройка, чтобы |время_кадра − время_приёма| держалось < ~50 мс
  (дрейф кварца/HSI контроллера до 1 %); если расхождение > 1 с — жёсткий переякорь. Переполнение 32-бит мкс
  (71 мин) учитывается. Время кадров внутри сессии не убывает больше чем на 1 мс (защита от скачков назад).

## 5. Файлы сессии: `<sessions>\<YYYYMMDD_HHMMSS>_<name>\`

- `frames.log` — формат candump:
  `(1789808098.170310) can0 0C9#0103E800000000A1` (std ID 3 hex-цифры, 29-бит — 8 цифр),
  FD: `can1 18DAF110##1<data>` (цифра флагов: 1 = BRS, 2 = ESI), remote: `can2 123#R8`, пустые данные: `can0 7DF#`.
  Время — эпоха в секундах, 6 знаков после точки. Буферизованная запись, сброс на диск не реже раза в секунду и при остановке.
- `events.jsonl` — по строке JSON на событие (см. §6), `t` — эпоха (секунды, float), `seq` — сквозной номер.
- `meta.json` — `{"board":"G4","name":"rpm","started":<t>,"stopped":<t|null>,"frames":N,"events":M,"channels":3,
  "version":"canhunt-1"}`; пишется при старте и обновляется при остановке.
- Остановка сессии: явная (`/session/stop`), при старте новой, при закрытии exe (корректно закрыть файлы).

## 6. События (память монитора: последние 2000; в сессии — все в events.jsonl)

Общие поля: `seq` (int, растёт с 1 от старта exe), `t` (float), `type`, `by` (`"claude"` | `"user"` | `"system"`).

| type | поля | кто создаёт |
|---|---|---|
| `session_start` | `name`, `dir`, `phase` (фаза, которая уже шла в момент старта записи, `""` — нет) | system |
| `session_stop` | `dir`, `frames` | system |
| `link` | `connected` (bool), `sniff` (массив `on` по каналам или null), `text` — связь с контроллером потеряна / восстановлена, сниффер выключился / включился, монитор повторил команды сниффера | system |
| `say` | `id` (= seq), `text`, `buttons` [{`label`, `phase` (строка или null)}], `input` (`"none"`/`"number"`/`"text"`), `input_label` | claude |
| `button` | `say` (id инструкции), `label`, `phase` | user |
| `input` | `say`, `value` (строка как введена) | user |
| `phase` | `label` (`""` — фаза закончилась) | claude или user (кнопка с phase порождает событие `phase` СРАЗУ после `button`) |
| `mark` | `label` | user («Отметка — сейчас!») или claude |
| `note` | `text` | user («Сообщение для Claude») или claude (показывается в журнале страницы) |
| `watch` | `fields` (как в /watch) | claude |

Фаза — именованный отрезок эксперимента: действует от события `phase` с непустым `label` до следующего `phase`
(или конца сессии). Кнопка с `"phase": "rpm2000"` начинает фазу, кнопка с `"phase": ""` заканчивает текущую,
`"phase": null` — фазу не трогает. Если запись начата посреди фазы, фаза в записи начинается с `session_start`
(его поле `phase`).

`link` пишет монитор сам (раз в 250 мс сверяет связь: порт открыт и диагностика моложе 2.5 с; `sniff.on` из неё).
Если идёт запись, сниффер был включён до обрыва, а после переподключения выключен (прошивка после сброса начинает с
выключенным), монитор повторяет команды `sniff`, прошедшие через `/cmd` после последнего «выключить всё».

## 7. HTTP-API монитора (JSON, UTF-8, только 127.0.0.1)

Существующие (не ломать): `GET /`, `/sniffer`, `/data`, `/status`, `/cfg` (G4), `/can/ids`, `/can/trace`, `POST /cmd`, `/can/log`, `/can/clear`.

Новые:
- `GET /assist` — страница `assist.html` (файл рядом с exe имеет приоритет над вшитым).
- `POST /session/start` `{"name":"rpm"}` → `{"ok":true,"dir":"...","started":t}` (идущую сессию сначала останавливает).
  Имя очищается до `[A-Za-z0-9_-]`, пустое → `session`.
- `POST /session/stop` → `{"ok":true,"dir":"...","frames":N,"events":M}` (если сессии нет — `{"ok":false}`).
- `GET /session` → `{"active":bool,"dir":str|null,"name":str|null,"started":t|null,"frames":N,"events":M,
  "phase":"текущая фаза","last_dir":str|null,"sessions_root":"..."}`.
- `POST /coach/say` `{"text":"...","buttons":[{"label":"Начал","phase":"rpm2000"},{"label":"Закончил","phase":""}],
  "input":"none","input_label":""}` → `{"ok":true,"id":seq}`. Без `buttons` → `[{"label":"Готово","phase":null}]`.
  Новая инструкция заменяет текущую на странице.
- `POST /coach/event` (от страницы) — одно из:
  `{"kind":"button","say":id,"label":"...","phase":null|"..."}`, `{"kind":"input","say":id,"value":"..."}`,
  `{"kind":"mark","label":"..."}`, `{"kind":"note","text":"..."}`, `{"kind":"phase","label":"..."}` → `{"ok":true,"seq":N}`.
  Монитор ставит `by:"user"` и время; для button с не-null phase добавляет событие `phase`.
- `POST /coach/phase` `{"label":"idle"}`, `POST /coach/mark` `{"label":"..."}`, `POST /coach/note` `{"text":"..."}` — от Claude (`by:"claude"`).
- `GET /coach/events?since=SEQ` → `{"seq":последний,"events":[события с seq>SEQ, не больше 500]}`.
- `GET /coach/wait?since=SEQ&timeout=SEC&types=button,input,mark,note` — длинный опрос: отвечает, как только есть
  событие с seq>SEQ, type из types и `by:"user"`; события `link` (монитор) и `say` (Claude) — тоже, но только если их
  тип указан в types явно (так `car.py ask` узнаёт о потере связи и о том, что инструкцию заменили); иначе по
  таймауту. Ответ `{"seq":..,"events":[...],"timeout":bool}`.
  timeout по умолчанию 60, максимум 900. Не блокирует остальные запросы (каждый запрос в своём потоке).
- `GET /coach/state` → `{"say":последний say|null,"answered":bool,"phase":str,"session":{как /session},
  "watch":[...],"seq":последний seq,"board":"G4","channels":3,"link":{"connected":bool,"port_open":bool,
  "sniff":[..]|null,"fps":[..],"demo":bool,"com_port":str}}`. `answered` — была ли уже кнопка/ввод на этот say;
  `link.connected` — порт открыт и диагностика свежая, `link.sniff` — `sniff.on` из неё, `link.fps` — кадров/с по каналам.
- `POST /demo/link` `{"up":false|true}` — только в `--demo`: имитация обрыва и восстановления USB (для проверок).

Безопасность HTTP: монитор слушает только 127.0.0.1; `Access-Control-Allow-Origin` не ставится; запросы с заголовком
`Host`, отличным от `127.0.0.1:<порт>` / `localhost:<порт>`, и не-GET-запросы с `Origin`, отличным от
`http://127.0.0.1:<порт>` / `http://localhost:<порт>`, получают 403 (страницы монитора и `car.py`/`curl` не затронуты:
у первых Origin свой, вторые его не ставят).
- `POST /watch` `{"fields":[{"name":"Обороты","spec":"0:0C9:1.7:16:be*0.25","unit":"об/мин"}]}` — заменяет список
  (не более 12 полей; неверный spec → `{"ok":false,"error":"..."}`); `GET /watch` → `{"fields":[...]}`.
- `GET /watch/values` → `{"t":Now,"values":[{"name","spec","unit","value":float|null,"raw":int|null,"age_ms":int|null}]}` —
  декодируется в мониторе из последних данных соответствующего ID (C#-реализация §2).

Ошибки: неизвестный путь — 404; неверный JSON — `{"ok":false,"error":"..."}` с кодом 200.

## 8. Демо-машина (`--demo`)

Имитатор для проверки без машины. Состояние следует текущей фазе событий (§6):
- обороты: фаза `rpmNNNN` → NNNN, `idle` → 800, `off` → 0, иначе 800; инерция τ≈0.5 с, шум ±15.
  ID 0x0C9, канал 0, 10 мс: байт 0 младшая тетрада — счётчик 0..15; байты 1-2 = rpm×4 big-endian
  (поле `0:0C9:1.7:16:be*0.25`); байт 3 = педаль газа 0..250 (×0.4 %), растёт вместе с целевыми оборотами;
  байт 7 = XOR байтов 0..6 ^ 0x5A.
- скорость: фаза `speedNN` → NN км/ч, иначе 0. ID 0x1F5, 20 мс, `0:1F5:0.0:16:le*0.01`.
- тормоз: фаза содержит `brake` → 1 (кроме `nobrake` / `no_brake` — так в PLAYBOOK названа фаза без тормоза). ID 0x2A0, 50 мс: `0:2A0:1.4:1:le`; байт 5 — счётчик 0..255; байты 6-7 константа.
- поворотники: фаза `left`/`right` → мигание 1.5 Гц. ID 0x3B2, 100 мс: бит 0.0 левый, 0.1 правый.
- дверь: каждое событие `mark` переключает состояние. ID 0x4C0, 200 мс: `0:4C0:2.3:1:le`.
- шум: ID 0x100 (10 мс, 8 случайных байт), 0x2F0 (20 мс, счётчик + медленный синус температуры), 0x7E8 изредка;
  канал 1 — FD-кадры с 29-битными ID (как сейчас), канал 2 — редкие кадры.
- У платы с одной шиной (H503) все кадры идут на канал 0.
- JSON диагностики — как у прошивки: сниффер при старте включён на всех каналах, все каналы «молча» (`silent:1`).
  Команды `sniff` из `/cmd` демо-машина выполняет сама (включает/выключает каналы, кадры выключенного канала не идут);
  прочие команды — «контроллера нет» (`ok:false`). `POST /demo/link {"up":false}` — «USB отключён» (ни кадров, ни
  диагностики), `{"up":true}` — «подключён», сниффер выключен, как у прошивки после сброса.

## 9. car.py (для Claude; только stdlib)

Порт: `--port`, иначе переменная `UC_PORT`, иначе порт, с которым car.py работал в прошлый раз (state.json — в том
числе демо 18473, заданный раньше через `--port`), иначе автопоиск среди 8473, 8723, 8503 и портов из файлов
`%TEMP%\UC_<плата>_Monitor[_demo].port` (монитор пишет туда свой порт; если стандартный занят, он берёт +1…+9) —
первый, кто ответил на `/status`. Вывод — кратко по-русски, ключ `--json` — сырой JSON. Состояние (последний
увиденный seq, порт) — `%LOCALAPPDATA%\canhunt\state.json`.

Коды выхода: 0 — ок / событие пришло; 1 — монитор недоступен; 2 — таймаут; 3 — ошибка (в том числе канал сниффера не
«молча»); 4 — вместо ответа пришло сообщение; 5 — инструкцию заменили новой (ask / wait --say); 6 — связь с
контроллером потеряна или сниффер выключен и за ~12 с не вернулись (ask / wait) — кадры не пишутся.

- `status` — плата, связь, сниффер по каналам (и «молча» ли каждый), кадров/с, сессия, фаза; последняя строка
  «Готово к работе.» или «НЕ ГОТОВО: …».
- `sniff on [--ch N] [--br K] [--fd 0|1] [--dbr K]` / `sniff off [--ch N]` → `POST /cmd` `{"cmd":"sniff",...}`; после
  подтверждения проверяет `can[i].silent`: канал не «молча» → «НЕ ГОТОВО», код 3. В демо команду выполняет демо-машина.
- `session start NAME` / `session stop` / `session` (печатает dir). `session start` предупреждает, если идёт фаза (она
  попадёт в запись) и если сниффер выключен или контроллер не подключён.
- `say TEXT [--buttons "Начал=rpm2000,Закончил=-,Не вышло"] [--input number|text --label TEXT]`
  (в `--buttons`: `=имя` — начать фазу, `=-` — закончить фазу, без `=` — фазу не трогать).
- `ask ...` — то же, что say, и сразу ждёт ответ на ЭТУ инструкцию (button/input с этим say) — `--timeout`, по умолчанию
  900 с. По пути печатает отметки, сообщения, нажатия кнопок прежних инструкций и фазы, начатые пользователем
  («ВНИМАНИЕ: …» — фаза могла смениться); код 5 — инструкцию заменили новой; код 6 — пропала связь с контроллером или
  сниффер (короткий обрыв с восстановлением — только строка «прерывались ~N с»).
- `wait [--since SEQ] [--timeout S] [--types ...]` — длинный опрос; по умолчанию since = последний увиденный seq,
  types = `button,input,mark,note,link`. Код выхода 0 — событие пришло, 2 — таймаут, 1 — монитор недоступен,
  6 — связь с контроллером / сниффер пропали. Печатает события построчно.
- `events [--since SEQ]`, `phase LABEL`, `mark LABEL`, `note TEXT`.
- `watch set "Обороты=0:0C9:1.7:16:be*0.25@об/мин" ...`, `watch add ...`, `watch clear`, `watch values` (печатает значения).

## 10. canhunt.py (анализ; numpy + PIL)

Вход: папка сессии, путь к `frames.log` (candump), или PCAN `.trc` (версии 1.1 и 2.x; время — смещение, мс),
или `latest` (последняя папка в каталоге сессий: `--sessions DIR`, иначе спросить монитор `GET /session` → `last_dir`).
Фазы и события читаются из `events.jsonl` рядом (если есть). Все подкоманды: `--ch`, `--id` фильтры, `--json`.
Потоки кадров — по (канал, 29-бит?, ID): 11- и 29-битный кадр с одним числом ID — разные потоки (`--id 00000123` —
только 29-битный). Запись без кадров (или без кадров на выбранных `--ch`/`--id`): `info` предупреждает, `compare`,
`track`, `marks`, `corr` завершаются ошибкой (код 1) — «не найдено» с кодом 0 легко принять за «сигнала нет в машине».

- `info` — длительность, кадры по каналам, число ID, фазы (имя, начало, длительность, кадров в фазе), отметки,
  введённые значения; предупреждения: фазы без кадров, паузы в кадрах дольше 1 с, ID одновременно 11- и 29-битный.
- `overview` — по каждому ID: частота, длина, по байтам: константа / счётчик / контрольная сумма (высокая энтропия,
  меняется почти в каждом кадре) / сигнал / флаги; маска меняющихся бит.
- `compare --a PHASE[,PHASE] --b PHASE[,PHASE]` — что отличает состояния: биты, стабильные внутри A и внутри B,
  но разные между ними; поля 8/16 бит с разделёнными распределениями. Счётчики и CRC отбрасываются (для бит — только
  они: чистый бит в «шумном» байте находится; поля 8/16 и мигание — ещё и без «шумных» байтов).
- `marks [--label L] [--phase P] [--window 1.0] [--before 0.3] [--lag 3.0]` — что меняется в окне у каждой отметки и
  почти не меняется вне окон (кнопки, двери, переключатели: пользователь N раз делает действие и жмёт «Отметка»).
  Сдвиг окна относительно отметок подбирается для каждого бита в пределах ±lag с (отметку жмут и до, и после действия).
  Оценка — с поправкой на случайность: окна покрывают долю записи coverage, оценка = полнота × (точность − coverage) /
  (1 − coverage); p — биномиальная вероятность случайного совпадения (с поправкой на перебор сдвигов). Нет бита с
  оценкой ≥ 0.3 и p < 0.05 → «устойчивой реакции не найдено». Часто меняющиеся биты (> 30 % кадров) и счётчики/CRC
  исключаются. `--phase P` — только отметки внутри фазы P, «вне окон» тоже считается только в ней (несколько кнопок
  в одной записи: у каждой своя фаза).
- `track --ref PHASE=VALUE ... | --ref-inputs` (можно вместе: ввод уточняет свою фазу) — поиск числового поля, линейно
  связанного с эталоном (обороты по тахометру и т. п.): перебор полей (выравненные по байту 8/16/24/32 le/be со знаком
  и без, 12-битные по тетрадам, 4-битные). Начало каждой фазы (`--skip`, 0.7 с; не больше половины фазы — фактическое
  печатается) отбрасывается, уровень фазы — медиана второй половины остатка, разброс — усечённое (10–90 %) СКО; первая и
  последняя треть сравниваются: тренд — «в начале фазы значение ещё менялось» (множитель округляется с допуском шире).
  Оценка = (1 − 2·СКО подгонки/размах) × (1 − 2·|a|·разброс/размах) × (1 − шаг младшего бита/размах) × монотонность ×
  доля фаз. Таймеры (тренд одного знака и одной скорости во всех фазах, объясняющий и разницу между фазами) штрафуются
  и помечаются; поля, монотонные по времени, при немонотонном порядке эталонов отбрасываются. Вложенные поля с тем же
  значением (постоянные биты, продолжение младшими битами) сводятся к одной границе (больше меняющихся бит, без
  постоянных ненулевых старших, стандартное выравнивание, меньше постоянных бит); поле с чужими младшими битами
  уступает своей «чистой» части; частично перекрывающий кандидат с втрое лучшей подгонкой показывается отдельно.
  Вывод: FACTOR/OFFSET с округлением до «красивых» (1, 0.5, 0.25, 0.125, 0.1, 0.05, 0.01, 1/128 …), готовая строка
  spec, таблица по фазам, варианты с масштабом и СКО подгонки. `--ref-inputs` — эталон из событий `input` (значение
  относится к фазе, активной в момент ввода; если фаз нет — к окну ±2 с вокруг ввода).
- `corr --field SPEC` — поля, коррелирующие с данным (сетка 50 мс).
- `plot (--field SPEC ... | --id CH:ID) [--out PNG]` — график по времени с закрашенными фазами и вертикалями отметок;
  для `--id` — «тепловая полоса» всех байтов ID. Печатает путь к PNG (по умолчанию в папке сессии `plots\`).
- `decode --field SPEC [--csv OUT]` — статистика поля по фазам.
- `export --field SPEC --name NAME` — строка для прошивки (`{ ID, start_byte, start_bit, bit_len, is_signed, factor, offset, "NAME" }`,
  только для `le`, для `be` — предупреждение) и строка DBC `SG_`.

Производительность: сессия 10 мин × 3000 кадр/с (≈1.8 млн строк) — разбор и `track` не дольше ~1 мин.

## 11. Передача кадров (TX) — как в любом CAN-сниффере

Передача пишет в шину машины, поэтому это отдельный, явно включаемый режим. По умолчанию канал слушает
«молча» (Bus Monitoring), передавать нельзя. Общая для прошивки G4/H723/H503 логика — модуль `app/can_tx.c/.h`;
платозависимая отправка кадра и перевод канала в Normal — в `can_app.c` каждой платы.

### 11.1. Активный режим канала (Normal)

Чтобы канал мог передавать, он поднимается в Normal той же командой sniff с флагом `tx`:
`{"cmd":"sniff","ch":N,"on":1,"br":125,"fd":0,"tx":1}`. При `tx:1` канал в Normal (op_silent=0): он ПОДТВЕРЖДАЕТ
кадры (ACK) и может слать; приём (accept-all, сниффер) при этом работает как обычно. Без `tx` (или `tx:0`) — по-прежнему
Bus Monitoring. `br`/`fd`/`dbr` задают скорость и формат шины (для кузовной шины обычно `br:125`, classic).
В диагностике `can[i].silent` = 0 у активного канала. Требование: на шине есть другие узлы, которые дают ACK
(в машине есть); на «мёртвой» шине из одного контроллера передача уйдёт в error-passive/bus-off — это видно в
`can[i].state/tec` и в счётчике ошибок.

### 11.2. Слоты передачи (в прошивке, до 8)

Слот: `{slot, ch, id, ext, fd, brs, dlc, data[8..64], period_ms, count, sent}`. `period_ms=0` — одиночная отправка;
`count=0` при периодической — бесконечно, иначе выключается после `count` отправок. Слоты обслуживает главный цикл
(частота отправки ≥ period_ms; джиттер до длительности цикла, ~10 мс). Одинаковый `slot` заменяет прежнее содержимое.

Безопасность прошивки:
- отправка идёт ТОЛЬКО если канал активен (enabled && !op_silent); иначе команда tx возвращает ошибку;
- если хост пропал (Vcp не готов) дольше TX_HOST_TIMEOUT_MS (2000) — ВСЕ слоты останавливаются (поток в шину не
  продолжается без ноутбука); после сброса и STOP слоты пусты;
- максимум 8 слотов; минимальный period_ms — 5 (защита от заливания шины); dlc ограничен форматом (classic ≤ 8).

### 11.3. Команды прошивки (строка в USB, разбирает can_tx.c)

- `{"cmd":"tx","ch":N,"id":HEX_ЧИСЛОМ,"ext":0/1,"fd":0/1,"brs":0/1,"dlc":D,"data":"0011..","period":P,"count":C,"slot":K}`
  — задать/заменить слот K (если `slot` нет — первый свободный). `id` — число (можно "0x384" строкой? нет: число, монитор
  переводит hex→int). `data` — hex, длина задаёт dlc, если `dlc` не указан. Ответ `{"resp":"ok","slot":K}` или ошибка.
- `{"cmd":"txstop","slot":K}` — стоп слота K; `{"cmd":"txstop"}` — стоп всех. Ответ `{"resp":"ok"}`.
- Статус в JSON диагностики: `"tx":{"active":[a0,a1,a2],"slots":[{"slot","ch","id","ext","fd","dlc","period","count","sent"} ...]}`
  (`active[i]` — можно ли слать на канал i: enabled && !silent). `id` в статусе — hex-строкой (например "384").

### 11.4. HTTP-API монитора (дополнение к §7)

- `POST /tx` `{"ch","id","ext","fd","brs","dlc","data":"0011..","period","count","slot"}` — монитор переводит id и шлёт
  контроллеру `{"cmd":"tx",...}`; ответ контроллера пробрасывается. Если целевой канал не активен — `{"ok":false,"error":
  "канал N не в режиме передачи — включите активный режим"}` (монитор проверяет по последней диагностике). Одиночная
  отправка — `period:0`.
- `GET /tx` → `{"active":[..],"slots":[..]}` (из последней диагностики контроллера).
- `POST /tx/stop` `{"slot":K}` или пустое тело — стоп слота/всех.
- Активный режим — через существующий `POST /cmd {"cmd":"sniff",...,"tx":1}` (§11.1).
- Демо (`--demo`): монитор имитирует контроллер — принимает слоты, «отправленные» кадры возвращает в поток сниффера
  того же канала (с флагами f/x по слоту), ведёт счётчик sent и отдаёт `tx` в диагностике; активный режим включается
  флагом tx:1. Периодические слоты в демо тикают по period_ms.

### 11.5. Страница /sniffer — панель «Передача»

Панель (в стиле страницы, отдельная карточка, свёрнута по умолчанию, с предупреждением «Передача пишет в шину машины»):
- выбор канала; поле ID (hex); флажки 29-бит, FD, BRS; поле данных (hex-байты, пробелы допускаются), рядом DLC (авто);
- «Отправить один раз»; поле «период, мс» + «Слать периодически» (+ «повторов», 0 = без предела); таблица активных
  периодических слотов с колонками канал/ID/данные/период/отправлено и кнопкой «Стоп» у каждого, кнопка «Стоп всё»;
- если канал не в активном режиме — вместо кнопок «Включить передачу на CAN N» (POST /cmd sniff tx:1 с подтверждением
  в две ступени) и явная плашка, что канал сейчас только слушает;
- клик по строке в «Ленте»/«По ID» подставляет ID, данные, флаги в панель (переслать принятый кадр, «как в сниффере»);
- при активной передаче — заметная плашка «● Идёт передача в CAN N» вверху.

### 11.6. car.py (дополнение к §9) — чтобы Claude тоже слал

- `car.py active on --ch N [--br 125] [--fd 0|1] [--dbr K]` / `active off [--ch N]` — активный режим (Normal) канала для
  передачи (это `sniff ... tx:1`); печатает предупреждение, что канал начнёт писать в шину. `status` показывает у канала
  «АКТИВНЫЙ (передача)» вместо «молча».
- `car.py tx CH ID DATA [--ext] [--fd] [--brs] [--period MS] [--count N] [--slot K]` — задать слот; без `--period` —
  одиночная отправка. `ID` и `DATA` — hex. Отказ (код 3) с понятным текстом, если канал не активен.
- `car.py tx-list` — активные слоты; `car.py tx-stop [SLOT]` — стоп слота или всех.
- Все команды tx печатают, что и куда ушло; car.py не переводит канал в активный сам (только по явной `active on`).

## 12. Разбор UDS в записи (только чтение)

Задача: по записи сессии (frames.log), снятой сниффером параллельно с работой AUTEL, разобрать диагностический обмен
(ISO-TP + UDS) и сузить область поиска нужного параметра: какие блоки на шине, что тестер у них читал/писал, какие
конфигурационные идентификаторы (DID) у них есть. Ничего не передаётся — это разбор уже записанного обмена. Модуль
`CAN_HUNT\canhunt_lib\uds.py`, подкоманда `canhunt.py uds`.

### 12.1. Сборка ISO-TP (ISO 15765-2)

Из кадров одного (канал, ID) собираются транспортные сообщения по PCI первого байта (для нормальной адресации;
расширенную/mixed не поддерживаем, помечаем):
- `0x0L` — single frame, длина L (для FD single с L=0 длина в след. байте);
- `0x1LLL` — first frame, полная длина 12 бит, дальше данные;
- `0x2N` — consecutive frame, номер N (0..15, циклический), склеиваются по порядку;
- `0x3S` — flow control (S=0 continue, 1 wait, 2 overflow) — в разбор данных не идёт, но отмечается.
Незавершённые цепочки (пропал CF, не хватило длины) помечаются, не молча теряются. FD-кадры (до 64 байт) поддержаны.

### 12.2. Пары «запрос-ответ» и адреса блоков

Диагностический ответ = запрос + 0x40 (или 0x7F негативный). Пары (ID запроса → ID ответа) выводятся из самого
обмена: ID, чьи сообщения начинаются с положительного/негативного отклика на недавний запрос с другого ID (окно ~1 с),
считаются ответом этого блока. Ничего не хардкодим под конкретную марку; типовые пары (0x7E0/0x7E8, функциональный
0x7DF, 29-битные 0x18DAxxyy/0x18DBxxyy) — только подсказки в отчёте, не жёсткие правила.

### 12.3. Разбор UDS

Таблица сервисов (0x10 DiagnosticSessionControl, 0x11 ECUReset, 0x14/0x19 DTC, 0x22 ReadDataByIdentifier,
0x27 SecurityAccess, 0x2E WriteDataByIdentifier, 0x2F InputOutputControlByIdentifier, 0x31 RoutineControl,
0x3E TesterPresent, 0x85 ControlDTCSetting и др.), коды отказа (NRC) с названиями. Для 0x22/0x62 и 0x2E/0x6E —
двухбайтовый DID и байты данных; для 0x31 — тип (start/stop/results) и RID; для 0x2F — DID и режим управления.

### 12.4. Подкоманды

- `canhunt.py uds <session|frames.log|trc> [--ch N]` — отчёт: список блоков (пары адресов, догадка о роли по типовым
  ID), по каждому — какие сервисы шли, в какие сессии заходил тестер, список прочитанных DID с байтами ответа, списки
  RID (routine) и записей 0x2E/0x2F. Плюс лента ISO-TP сообщений с временем. Флаги `--ecu ADDR`, `--service HEX`, `--json`.
- `canhunt.py uds-did <session> --ecu ADDR` — таблица всех DID этого блока и последних прочитанных байт (дамп конфигурации).
- `canhunt.py uds-diff <A> <B> [--ecu ADDR]` — сравнить дампы DID двух записей (например, машина с маркерами и без, или
  до/после переключения опции): какие DID и какие байты/биты различаются → кандидаты в искомый конфигурационный бит.
  Это и есть «сужение области»: различие в конфигурации между двумя состояниями.

Активной отправки UDS в этом разделе нет. Если по найденному DID/сигналу понадобится что-то повторить своим
контроллером — это делается уже разделом §11 (передача), точечно и осознанно.
